## Structure/Architecture

- `src/ExecutivePlanning.Core` is organized exactly as its file layout suggests: `Domain/` holds plain entity classes (`User.cs`, `Project.cs`, `Objective.cs`, `WorkItem.cs`, `ChecklistItem.cs`, `TaskOwner.cs`, `Meeting.cs`, `ProgressNote.cs`, `StatusChange.cs`, `Enums.cs`); `Data/` holds `PlanningDbContext.cs`, `PlanningDbContextFactory.cs`, and `DbSeeder.cs`; `Services/` holds `PlanningService.cs` (the single façade class for all CRUD + reporting), `PlanningValidation.cs` (`PlanningRules` static validators + `ValidationException`), and `Reports.cs` (`AccountabilityRow`/`ProjectSummary` DTOs).
- `PlanningDbContext.OnModelCreating` (lines 24-195, read in full) declares real, working relational rules matching the domain's intent — e.g. `e.HasOne(p => p.Owner).WithMany(u => u.OwnedProjects).HasForeignKey(p => p.OwnerId).OnDelete(DeleteBehavior.Restrict);` for Project→Owner, and `e.HasOne(t => t.Project).WithMany(p => p.Tasks)...OnDelete(DeleteBehavior.Cascade);` for Project→WorkItem — these cascade/restrict/set-null behaviors are exercised directly by tests such as `Deleting_project_cascades_to_tasks_and_notes` and `DeleteProject_removes_everything_under_it` in `PlanningServiceTests.cs`.
- `PlanningService.cs` is a single ~370-line class (read in full) that both Desktop apps call directly — there is no repository/unit-of-work abstraction layer; ViewModels hold a `PlanningService` reference and call its methods directly (e.g. `MainViewModel.AddNote()` calls `_service.AddNoteAsync(...)`).
- Two independent Avalonia front ends both reference Core via `<ProjectReference Include="..\ExecutivePlanning.Core\ExecutivePlanning.Core.csproj" />`:
  - `src/ExecutivePlanning.Desktop`: a single `MainWindowViewModel.cs` (218 lines, read in full) drives one tabbed `MainWindow.axaml`, matching the README's description of "Tasks · Meetings & Notes · Accountability" tabs.
  - `src/ManagerPlanner.Desktop`: a Win95-style MDI shell — `Controls/MdiHost.cs` is a `Canvas` subclass managing child-window cascade/tile/restore, `Controls/MdiWindow.cs` is a custom `HeaderedContentControl` implementing its own drag/resize/maximize/minimize logic (private fields `_dragging`, `_maximized`, `_restore`), and `Views/MainWindow.axaml.cs`'s `OnOpened` handler wires up four child windows (`ProjectsView`, `PlannerGridView`, `TaskNotesView`, `AccountabilityView`) into that host.
  - The two apps use **separate SQLite database files by explicit design** — `ManagerPlanner.Desktop/App.axaml.cs` states directly in comment: *"v2 has extra tables (Objectives, ChecklistItems, TaskOwners), so it uses its own database file — EnsureCreated does not migrate the v1 file in place,"* writing to `%LOCALAPPDATA%\ManagerPlanner\planner.db` versus ExecutivePlanning's `%LOCALAPPDATA%\ExecutivePlanning\planning.db` (per `PlanningDbContextFactory.DefaultDatabasePath()`).
  - Both ViewModels use CommunityToolkit.Mvvm source generators consistently, but `ManagerPlanner.Desktop/Views/MainWindow.axaml.cs` also wires manual events from the ViewModel to view-owned dialogs — e.g. `vm.MessageRequested += async msg => await MessageBox.Show(this, "Manager Planner", msg);` — blending generator-based MVVM with direct event-bridging for modal dialogs.
- `tests/ExecutivePlanning.Tests` only exercises `ExecutivePlanning.Core` — its manifest's only `ProjectReference` is to `ExecutivePlanning.Core.csproj`, and `PlanningServiceTests.cs`/`TestDb.cs` are the only real test files (`UnitTest1.cs` is an intentionally-empty placeholder, per its own comment).

## Domain

Inference: This is a manager's team-accountability / task-tracking tool built around cross-checking verbal promises against actual delivery — grounded in `ProgressNote.cs`'s doc comment: *"This is the heart of the accountability feature: the Manager can flag that the team member promised something by a certain date, then later cross-check promise vs delivery,"* and in `PlanningService.GetAccountabilityReportAsync` (lines 269-330), which computes `PromiseKept`/`PromiseBroken`/`IsOverdue` per task from the latest `ProgressNote` marked `IsPromise`.

Inference: The domain models a lightweight OKR-like hierarchy — Project → Objective → WorkItem (task) → nested ChecklistItem — inferred from `Objective.cs`'s comment *"Sits between Project and WorkItem so work is grouped the way a manager plans it: Project → Objective → Task"* and from `ChecklistItem.cs`'s self-referencing `Parent`/`Children` fields enabling arbitrary nesting of sub-items.

Inference: The seeded sample data in `DbSeeder.cs` (read in full) suggests the tool targets at least two different management contexts, not just software delivery: internal engineering-style tracking (`"Q3 Platform Migration"` with tasks like `"Design new database schema"`, `"Build data-access / API layer"`) and external account/relationship management (`"Key Account — Tracsis"` project with an objective titled `"Build relationships beyond Chris"` and a stakeholder-mapping nested checklist naming roles like `"Jenny — Head of QA"` and `"Damian — Chris's boss"`) — i.e. the product is pitched broadly at "manager holds people accountable for commitments," not narrowly at software project management.

Inference (low confidence): The Win95-style skin in `ManagerPlanner.Desktop` (`Themes/Win95.axaml`, `MessageBox.cs`'s `#c0c0c0` grey dialog background and `"Tahoma, 'MS Sans Serif', Geneva, Verdana, sans-serif"` font stack, and `MdiHost`'s cascade/tile semantics) may be a deliberate nostalgia/personality choice for a "no-nonsense manager" persona rather than a technical necessity — this is a stylistic guess; nothing in the docs explicitly states the design rationale beyond the README calling it a "classic Win95-style MDI variant."

## Risks/Tech-Debt

- **No EF Core migrations exist anywhere in the repo** (a filesystem search for any `*migration*`-named file under `src/` returned nothing), and `PlanningDbContextFactory.Create` only calls `ctx.Database.EnsureCreated()`. The codebase's own documented workaround for schema evolution — stated directly in `ManagerPlanner.Desktop/App.axaml.cs` — is to fork a brand-new database file per app version rather than migrate in place. This is a structural risk: any future schema change to shared `Core` entities is likely to again require a new DB file/location instead of an in-place upgrade path.
- **Zero automated test coverage for both UI layers.** `tests/ExecutivePlanning.Tests.csproj`'s only `ProjectReference` is to `ExecutivePlanning.Core.csproj`, and no test files exist under `src/ExecutivePlanning.Desktop` or `src/ManagerPlanner.Desktop`. All facts in `PlanningServiceTests.cs` exercise `PlanningService`/`DbSeeder` only — ViewModel command bodies (e.g. `MainViewModel.AddNote()`, `DeleteProject()`, `ResetSampleData()`), the hand-rolled drag/resize/maximize logic in `Controls/MdiWindow.cs`, and the dialog flow in `Controls/MessageBox.cs` are unexercised by any automated test.
- **Two near-duplicate front ends over the same Core**, confirmed by directly comparing `MainWindowViewModel.cs` (ExecutivePlanning.Desktop) against `MainViewModel.cs` (ManagerPlanner.Desktop): both independently re-implement near-identical `InitializeAsync`/`LoadProjectsAsync`/`AddNoteAsync`-style wiring against the same `PlanningService`. The README frames `ExecutivePlanning.Desktop` as "the original" and `ManagerPlanner.Desktop` as "newer," but both remain in the `.sln` and in the tree, and it is undocumented whether `ExecutivePlanning.Desktop` is still meant to be maintained or is legacy code being kept temporarily.
- **Stale README cross-references confirmed by direct comparison with git state:** README.md states ManagerPlanner.Desktop lives "on branch `feature/manager-todo-sdi-mdi`," but `git branch -a` on this checkout shows only `main` / `remotes/origin/main`, and the five most recent commits (`61c39a1`, `f6f3f05`, `4f22b49`, `83bf0d3`, `859fae2`) show the ManagerPlanner.Desktop work already landed on `main`. Separately, README.md links to `design/manager-todo-ui-plan.md`, but commit `f6f3f05 "Remove design/ from main (kept on docs/manager-planner)"` removed that directory from `main` — confirmed by the file enumeration showing no `design/` directory at the repo root — so that link is currently dangling.
- **`PlanningService` has no interface/abstraction** — it's a concrete class taking a concrete `PlanningDbContext`, and it is directly `new`'d up in both `App.axaml.cs` files rather than via a DI container (e.g. `var service = new PlanningService(db);`). Fine for the app's current size, but it means any future automated testing of the ViewModels themselves (not just the service) would require a real `PlanningDbContext`/SQLite connection, since there is no seam to substitute a fake.
- **Bespoke UI-framework code with no test safety net.** `ManagerPlanner.Desktop/Controls/MessageBox.cs` and `Controls/MdiWindow.cs` hand-roll modal dialogs and MDI window chrome (drag via `PointerPressed`/`PointerMoved`/`PointerReleased`, resize via a `Thumb`'s `DragDelta`, maximize/restore state tracked in a private `_restore` `Rect`) rather than using Avalonia's built-in `Window`/dialog primitives. This is functional based on the code read, but bespoke chrome logic like this tends to accumulate edge-case bugs (nothing in the read code handles keyboard navigation or persisting z-order across restarts) that are easy to miss without any UI-level test coverage.

## Suggested First Changes

- Start with `src/ExecutivePlanning.Core/Services/PlanningService.cs` together with `tests/ExecutivePlanning.Tests/PlanningServiceTests.cs` — `PlanningService.cs` is the single façade nearly every feature (CRUD, accountability, checklist, owners) funnels through, and `PlanningServiceTests.cs` already demonstrates the `TestDb`-based pattern (real in-memory SQLite via `SqliteConnection("DataSource=:memory:")`, not mocks) that any new business-logic change should follow.
- For accountability-report changes, read `Services/Reports.cs` (`AccountabilityRow.Verdict`, lines 37-47) together with `PlanningService.GetAccountabilityReportAsync` (lines 269-330) — the verdict logic (Kept/Broken/Pending/Overdue) and its computation are tightly coupled, and the existing `Accountability_flags_broken_promise` / `Accountability_flags_kept_promise` / `Accountability_uses_latest_promise` tests in `PlanningServiceTests.cs` serve as the executable spec of current behavior.
- Before touching either Desktop UI, clarify (this is undocumented) whether `ExecutivePlanning.Desktop` is still a live target — the five most recent commits (`61c39a1`, `f6f3f05`, `4f22b49`, `83bf0d3`, `859fae2`) and the `publish/` scripts all target `ManagerPlanner.Desktop` only, suggesting new UI work should likely go there.

- Fix the two dangling README references identified above (the `feature/manager-todo-sdi-mdi` branch that doesn't exist on this checkout per `git branch -a`, and the `design/manager-todo-ui-plan.md` link removed by commit `f6f3f05`) — a cheap, low-risk first change that removes a confusing onboarding trap for new contributors reading `README.md`.
