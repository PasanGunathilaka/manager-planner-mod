# Manager Planner / Executive Planning — Golden-Master Capture Harness

Generated by `/specclaw:baseline --harness`. This project captures golden-master fixtures for the
43 scenarios documented in `.specclaw/baseline/scenarios.md` (`GM-001` through `GM-043`) — **it
does not run itself; a human runs it.**

## What this is

- References the legacy app's core/domain library, `ExecutivePlanning.Core.csproj`, directly —
  never the UI projects (`ExecutivePlanning.Desktop`, `ManagerPlanner.Desktop`).
- One xUnit `[Fact]` per scenario (`GM-NNN`), arranging state via a real in-memory SQLite
  database (the exact `TestDb`/`SqliteConnection("DataSource=:memory:")` pattern already proven
  in the legacy repo's own `tests/ExecutivePlanning.Tests/TestDb.cs`), then writing a fixture
  JSON file via `FixtureWriter` — the fact does not need to assert pass/fail to be useful;
  capturing the fixture *is* the point (each fact also carries its own basic sanity `Assert.*`
  calls, since the legacy behavior is already known from `scenarios.md`/the legacy repo's own
  test suite, not because the assertion is this harness's primary output).
- Every fixture records its own capture timestamp, an anchor date, the **legacy** repo's commit
  SHA (not this repo's), and the runtime version, so `/specclaw:baseline --record` can build a
  manifest and a human can judge whether a later replay diverged for a real reason or an
  environment/timing reason.

## Cross-repo `ProjectReference` — why a relative path, and its fragility

This harness lives in the rebuild repo (`manager-planner-mod`), but the legacy code it exercises
(`ExecutivePlanning.Core`) lives in a **sibling repo**, `manager-planner`, confirmed on this
machine at:

```
C:\Learnings\Projects\manager-planner-mod   <- this repo (harness lives at .specclaw/baseline/harness)
C:\Learnings\Projects\manager-planner       <- the legacy repo (harness references its Core project)
```

`Harness.csproj` uses a **relative** `ProjectReference`:

```
..\..\..\..\manager-planner\src\ExecutivePlanning.Core\ExecutivePlanning.Core.csproj
```

This assumes both repos are checked out as siblings under the same parent directory — which is
already this project's own established convention (see this repo's memory note: "real legacy
source is on disk at `../manager-planner`, not just doc summaries"). It is **not** portable to a
machine where the two repos are checked out in a different relative layout. If that ever breaks:

- Re-point the single `<ProjectReference>` line in `Harness.csproj` to wherever
  `ExecutivePlanning.Core.csproj` actually resolves on the machine running the capture (an
  absolute path works too — `dotnet build`/`dotnet test` do not care), or
- Set an environment variable / MSBuild property for the legacy repo root and reference that
  instead, if this harness is ever run across multiple machines with inconsistent layouts.

`FixtureWriter.GetLegacyCommitSha()` resolves the same sibling path independently (via
`Paths.HarnessDir`) so the recorded `legacy_commit_sha` is always the **legacy** repo's own HEAD,
not this rebuild repo's.

## Commands

```bash
cd .specclaw/baseline/harness
dotnet build
dotnet test
```

Fixtures land in `.specclaw/baseline/fixtures/`, one file per scenario ID (`GM-001.json` through
`GM-043.json`). After running, go back to the project root and run:

```
/specclaw:baseline --record
```

to validate the captured fixtures against `scenarios.md` and produce
`.specclaw/baseline/manifest.json`.

## Determinism reminders (see `.specclaw/baseline/seams.md`)

- **GM-006/GM-007** pin `PlanningRules.ValidateNoteDate`'s own injectable `nowUtc` parameter to a
  fixed literal (`2026-07-30T00:00:00Z`) — the cheapest, highest-fidelity capture in the
  codebase; no rebuild-side change required to replay these identically.
- **GM-013 through GM-018, GM-024, GM-028, GM-040** express every date as an offset from
  `FixtureWriter.AnchorDate` (`DateTime.UtcNow.Date`, captured once per test run) rather than
  calling `DateTime.UtcNow` directly in each fact — per seams.md CB-1/CB-2's Option 3 mitigation.
  This is necessary because the legacy `PlanningService.ChangeStatusAsync` (`CompletedUtc`) and
  `GetAccountabilityReportAsync` (`now`) both read `DateTime.UtcNow` directly with **no
  injectable override in the legacy source** — this harness cannot inject a clock into code that
  doesn't accept one; it can only anchor its own *inputs* to a single captured "today" so a
  fixture's boundary (same-day vs. one-day-off) reproduces correctly regardless of which calendar
  day the fixture is later replayed on. **This gap (no injectable clock anywhere in
  `PlanningService`) should become a `TARGET-GAP` question for `/specclaw:clarify`**, per
  seams.md CB-1: the rebuild's equivalent service is expected to accept an injectable
  `Clock`/`TimeProvider`, which would let a future harness pin the exact captured instant instead
  of only the calendar-day boundary.
- **GM-018**'s sort-tie scenario deliberately does not assert which of the two tied rows comes
  first — it records whatever order the legacy SQLite/EF Core execution actually produces. Do
  not "correct" this fixture on replay; it exists specifically to pin CQ-024's undocumented
  tie-break as observed, not as designed.
- **GM-020/GM-023** record `CompletedUtc` timestamps in the fixture's `output` but list them
  under `normalized_fields` — only non-null-ness is asserted/business-relevant per seams.md CB-1's
  Option 2 (no documented rule reads the literal timestamp back for a decision).
- **GM-041/GM-042/GM-043** are deliberately restricted to structural counts/existence — `DbSeeder`
  has no injectable anchor date anywhere in its public surface (seams.md CB-5), so none of these
  scenarios assert a date-derived Verdict/Overdue outcome from the seeded data.

## Extending to other stacks

This generator currently targets **.NET only** (detected via `codebase-report.md`'s Tech Stack
section, which confirms .NET 8 + xUnit + EF Core/SQLite for this repo). To extend
`/specclaw:baseline --harness` to another stack, the extension point is
`agents/baseline-designer.md`'s **Mode: harness** section — add a stack-detection branch there
and a matching scaffold under `templates/harness/` for that ecosystem's test/capture-project
conventions. Nothing in `bin/specclaw-baseline` or the scenario-derivation logic in Mode A
(design) is .NET-specific; only this harness code generator is.
