## Issues Found

1. **The Delete button's click frequently navigates to the project detail page instead of opening the confirmation dialog, in a live-running instance of the app.** `Projects.razor`'s `<span @onclick:stopPropagation="true" @onclick:preventDefault="true">` wrapping the `MudIconButton` is nested inside a `MudListItem` that renders as a real `<a href="/projects/{id}" class="mud-list-item mud-list-item-clickable mud-ripple ...">` (confirmed by reading the live DOM's `outerHTML`). This app uses the unified .NET 8 Blazor Web App model (`App.razor`: `<Routes @rendermode="InteractiveServer" />`, `blazor.web.js`), which enables **enhanced navigation** by default — a document-level click interceptor for same-origin anchor tags that is a separate mechanism from a component's own `@onclick` event modifiers. In 9 live click attempts (three methods: CDP click via resolved element ref, CDP click at the exact `getBoundingClientRect()`-derived coordinate, and a direct JS `.click()` call on the actual `<button>` node — the last of which bypasses all coordinate ambiguity and still navigated 4/4 times), the click reached the anchor's navigation 7 times and only twice was suppressed (and even then, no dialog appeared, meaning the button's own `OnClick` handler was not observed to fire successfully either). No project was ever deleted without confirmation in any attempt, so this is a "the delete affordance doesn't work reliably" bug, not a data-safety bug. **Fix:** don't rely on `@onclick:stopPropagation`/`@onclick:preventDefault` on a nested element to defeat a `Href`-rendering ancestor under enhanced navigation. Options, in rough order of preference: (a) opt the anchor out of enhanced navigation explicitly (Blazor supports `data-enhance-nav="false"` on the link or an ancestor — verify whether `MudListItem`/`MudList` exposes a passthrough attribute for this, or wrap the list in a `<div data-enhance-nav="false">`); (b) stop using `MudListItem`'s `Href` for row navigation and instead drive navigation from an explicit `OnClick` handler using `NavigationManager.NavigateTo(...)`, guarded by a flag the delete handler can set synchronously in C# before returning, removing the dependency on DOM-level event-modifier races entirely; (c) restructure the row so the delete button is a sibling of the anchor rather than nested inside it (e.g., a flex row with the `<a>` covering only the name/description and the delete button entirely outside the anchor's hit area), which sidesteps the "prevent bubbling into an ancestor anchor" problem structurally instead of racing against it. Whichever fix is chosen, it should be **re-verified with an actual live click-through** (as this pass did) rather than by inspecting server-rendered HTML markers alone, since that inspection method is exactly what let this regression through the build's own verification pass undetected.
